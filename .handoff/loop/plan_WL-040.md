# WL-040 — Canonical session export/import (portable JSON IR for cross-instance interchange)

_Plan written by weave-planner. Worktree: `/home/drdave/Desktop/meta/weave-wl038-042` (branch `wl-038-042-batch`, base origin/develop @ 83bf523). Planning only — no delivery._

## Goal

Add a **default-build** `weave session export` / `weave session import` capability that serializes a single session/peer identity's logical state (its messages, plus its tracked asks) into a **canonical, versioned, portable JSON document** and re-imports that document into a *different* weave instance — round-trippable and idempotent. This is `cross_agent_session_resumer` (casr) parity. It is distinct from WL-034 (HTML *presentation* export) and WL-035 (whole-DB *binary* snapshot backup/restore): WL-040 is a **logical, schema-versioned interchange format** for portability across distinct weave DBs whose row ids and minted correlation ids will not match. The pure (de)serialize layer lives in a new `weave-core/src/session.rs` (mirroring the `export.rs`/`archive.rs` pure-module precedent); all I/O (file read/write, store reads, store inserts) lives in a new `weave/src/session.rs` bin-layer handler (mirroring `backup.rs`). No new crate, no new dependency, no new standing MCP tool.

## Key decisions (resolve up front)

1. **Canonical schema = a versioned envelope; v1 minimal portable set = messages + asks.**
   - `weave_session_export: 1` (the format discriminator/magic) and `schema_version: 1` (forward-compat — a future field add bumps it; importer accepts `<=` its known max and ignores unknown fields via `#[serde(default)]`, the established `Message`/`Ask` additive pattern).
   - **Messages** are the core payload (the same per-identity set `weave session export` reads via `Store::history(me, None, limit)` — exactly what WL-034 exports).
   - **Asks** are included because a "session" in weave is a peer identity *and its tracked-ask threads* (`list_asks`). Including asks is what makes this a *session* resumer rather than a message dump.
   - **Memory is OUT of scope for v1 — and this must be stated explicitly in the plan/docs.** `weave-core/src/memory.rs` is a **filesystem** store (per-`MemoryScope` files under the config dir), NOT a DB table; it is not reachable through the `Store` trait and is identity/persona/project-scoped on the local host. Folding it into a DB-derived JSON export would couple two unrelated stores and expand scope/risk. v1 exports DB-resident session state only; `schema_version` leaves the door open to add a `memory: [...]` block later without breaking importers. (casr parity is satisfied by messages+asks; memory portability is a tracked follow-up, not a silent omission.)
   - **Peers are NOT exported as importable rows.** A peer row is host/mux/pane-local liveness state (`mux`, `target`, `socket`, `pid`, `host`, `birth_cert`) that is meaningless — and a security hazard (identity/birth-cert takeover, see `register_peer_full` doc) — in another instance. The envelope records the exported `identity` as a plain string only.

2. **Import reuses `Store::send` — ZERO new Store method, ZERO schema change (strongly preferred; one-handler law).**
   `Store::send(sender, recipient, subject, body, idempotency_key, trace_id)` already takes sender/recipient as args, mints a fresh local autoincrement id, and dedups on `idempotency_key`. That is exactly the import primitive: insert each exported message under the importing identity with id-remapping handled automatically (new local ids) and idempotency handled by the existing `idempotency_key` dedup. **No new dual-backend Store method is needed for messages.** This keeps WL-040 entirely off the `store.rs`/`store_libsql.rs` mirror burden.
   - **Asks on import (v1 policy): import asks as data-fidelity is HARD without a Store insert that takes a foreign correlation id, which would be a new dual-backend method and a state-machine hazard.** Decision: **v1 imports messages only; asks are exported for fidelity/inspection and are reconstructed-on-import only as their underlying question/answer *messages*** (which `history` already returns as normal `messages` rows). The `asks: [...]` block is written on export (portable record) and, on import, is **validated + skipped with a counted note** rather than replayed through the ask lifecycle. This avoids inventing a `Store::import_ask` that would have to mint/accept correlation ids and force `AskState` transitions out of order. If the verifier/guardian deems ask-thread replay in-scope for casr parity, that becomes a *follow-up* (WL-040b) with a real dual-backend `Store` method — flagged here, not smuggled in. **Open question #1 below.**

3. **Conflict / idempotency policy on re-import = skip-existing by `idempotency_key`, else insert.**
   - Every exported message carries its source `idempotency_key` and `trace_id` if present. On import, `Store::send` is called **with the source `idempotency_key`**; the existing global-unique dedup makes a re-import of the same document a no-op for already-present rows (returns the existing id). This delivers idempotent re-import for free.
   - **A message with NO source `idempotency_key`** cannot be deduped by key. Policy: **synthesize a deterministic import key** = `wl040:<source_identity>:<source_msg_id>` (bounded, `[A-Za-z0-9_:]`, well under `MAX_BODY`) so that re-importing the same document twice is still idempotent (the synthesized key collides on the second pass). This is the conflict guard for keyless legacy messages. Document this synthesis in the format doc.
   - **Identity remap:** import inserts under the **importing** identity (resolved `--as <id>` flag, else `resolve_me()`), NOT the source identity, so a session can be resumed under a new name. The envelope's `identity` is advisory provenance. Both `sender` and `recipient` are rewritten per the remap rule: messages the source *sent* keep their recipient; messages the source *received* are inserted with `recipient = <importing id>`. **Open question #2 below** (exact sender/recipient rewrite rule for the broadcast and third-party cases).

## Dual-backend? — **NO** (asserted, not assumed)

WL-040 adds **no** `Store` trait method and **no** schema change. Export reads through existing `history` + `list_asks`; import writes through existing `send`. Therefore **`store.rs` and `store_libsql.rs` are untouched** and the libSQL build needs no mirrored edit. The CI libSQL job (`cargo test --no-default-features --features libsql`) still must pass because the new `weave-core/src/session.rs` is backend-agnostic and the integration test drives the compiled binary regardless of backend — so the integration/security tests run under both backends unchanged. *(If Open Question #1 resolves toward replaying ask threads on import, that WOULD introduce a new dual-backend `Store::import_ask` and this section flips to YES — re-plan as WL-040b before doing so.)*

## Invariants in scope

- **No shell, ever** — `weave/src/session.rs`: import/export spawn no external programs; pure file + store I/O. (No argv construction at all; assert by absence.)
- **Parameterized SQL** — `weave/src/session.rs` import path performs all writes through `Store::send` (already fully `params!`-bound). No new SQL literal is introduced anywhere. The envelope's `identity` and message bodies never reach SQL except as bound params via `send`.
- **Input is capped (the central import invariant)** — `weave/src/session.rs` `run_import`: every field from the *untrusted* JSON file is bounded before it touches the store — `check_ident("identity", …)` on the importing id and every per-message sender/recipient; body length `<= MAX_BODY` (reject or this is a hard error); subject capped; `idempotency_key`/`trace_id` validated to the minted shape (`trace_id_valid` / ascii `[A-Za-z0-9_]`-class) so a hostile key can't be bound. An import file is **untrusted external input** — treat it with the same suspicion as a network payload.
- **Path-traversal / arbitrary-write guard** — both `--out` (export) and `--in` (import): UTF-8-validate the path, `--force` overwrite guard on `--out` (copy `backup.rs::run_backup`), and `--in` is read-only (no extraction of embedded paths — unlike WL-035's archive, this format embeds NO filenames, so there is no in-payload traversal vector; assert that the format carries no path fields). Write export atomically via sibling-temp + rename.
- **stdout discipline** — CLI prints human summaries to stdout (fine; this is the CLI surface, not MCP). No MCP tool is added, so the MCP stdout-only-JSON-RPC invariant is not touched. (Confirm in the plan that **no** `weave_*` standing tool and **no** `tool_catalog()` entry is added — CLI parity is the zero-standing-cost path; MCP exposure, if ever wanted, is a catalog-only follow-up, never a new standing tool.)
- **Destructive-op gating** — import is *additive* (inserts; idempotent on re-run) so it is NOT a destructive op and needs no `confirm`. Export `--force` only overwrites the user-named output file, guarded as above. No `--scope all`-class hazard.
- **Token-light MCP surface** — unaffected: zero new standing tools, zero catalog growth. Note this explicitly so the `standing_mcp_surface_is_within_token_budget` test is known-unaffected.

## Test layers required (per `docs/TESTING.md` §8)

1. **Unit — pure round-trip (`weave-core/src/session.rs` `#[cfg(test)]`):**
   - `serialize_session → to_json → from_json` reproduces identical messages (id/ts/sender/recipient/subject/body/idempotency_key/trace_id/priority preserved).
   - `from_json` **rejects** a wrong/missing `weave_session_export` magic and a `schema_version` greater than `SCHEMA_VERSION` (forward-compat guard); **accepts** an envelope with extra unknown fields (additive `#[serde(default)]` tolerance).
   - `synth_idempotency_key` is deterministic and within the id-shape cap.
   - Empty-session export/import (no messages, no asks) round-trips to a valid empty envelope.
2. **Integration — cross-DB portability (`weave/tests/integration.rs`):** the headline proof. Drive the compiled binary: (a) `weave send`/seed messages into temp DB **A** under identity `alice`; (b) `weave session export --out f.json --for alice` against DB-A; (c) point `WEAVE_DB` at a *fresh* temp DB **B**; (d) `weave session import --in f.json --as alice` into DB-B; (e) assert `weave history`/`inbox` on DB-B shows the imported messages — proving portability across two distinct DBs with id remapping. Add a **re-import idempotency** case: importing the same file into DB-B twice inserts each message once (skip-existing by idempotency_key / synth key). Add a `--dry-run` case (reports counts, writes nothing).
3. **Security (`weave/tests/security.rs`):**
   - **Input caps:** an import file with an over-`MAX_BODY` body, an over-length/control-char identity, and a malformed `idempotency_key`/`trace_id` is **rejected cleanly** (non-zero exit, no panic, no partial-write corruption of DB-B).
   - **No injection:** an import body containing `'; DROP TABLE messages; --` and one containing `$(…)`/backtick shell metachars imports as **literal text** (round-trips byte-identical; DB intact; no shell spawned). A SQL-metachar identity is rejected by `check_ident` before any bind.
   - **Path traversal / arbitrary write:** `--out ../../etc/passwd`-style and absolute-path cases are governed by the `--force`/parent-exists guard exactly like `backup`; `--in` pointing at a non-JSON / oversized / truncated file errors cleanly without partial DB mutation. Confirm the format embeds **no** path fields (so a crafted file can't direct a write elsewhere).
4. **Prop (`weave/tests/prop.rs` or core proptest):** optional but recommended — property: for any `Vec<Message>` (arbitrary bodies incl. unicode, embedded quotes, `</script>`-class strings, NULs filtered by caps), `from_json(to_json(serialize_session(…)))` preserves the message set (the round-trip invariant). This is the WL-040 analog of the injector exact-argv property.

## Risks / open questions

1. **Ask replay fidelity (the main scope decision).** v1 plan: export `asks` for record/inspection but import **messages only** (asks not replayed through the lifecycle), because faithful ask import needs a new dual-backend `Store` method that mints/accepts foreign correlation ids and drives `AskState` transitions out of natural order — real risk to the ask state machine. *Proposed resolution:* ship messages-only import in v1 (the casr core — resume the conversation), record asks in the envelope for forward-compat, and track ask-thread replay as WL-040b. **Implementer must NOT invent a `Store::import_ask` without re-planning.** Confirm with leader.
2. **Sender/recipient remap rule for broadcast and third-party messages.** When the exported set includes (a) broadcasts the source sent, and (b) messages between the source and a *third* peer, the exact rewrite under `--as <newid>` needs nailing: simplest safe rule = preserve `sender`/`recipient` verbatim EXCEPT rewrite occurrences of the *source identity* to the *importing identity*. This keeps third-party names intact and resumes the session under the new name. Spell this rule out in the format doc; the implementer should follow it exactly. (Edge: if `--as` equals the source identity, it's an identity-preserving import — the common cross-machine resume case.)
3. **Top-level name collision.** A top-level `Export` (HTML, WL-034) already exists. The plan deliberately groups the new ops under `weave session export/import` (a `SessionCmd` subcommand) to avoid overloading `weave export`. Confirm the orchestrator is fine with the `session` group name (alternative: `weave export --json` flag on the existing command — rejected here because export *and* import need a home and a flag can't host import).
4. **Memory portability gap.** v1 excludes filesystem-backed agent memory by design (different store, host-scoped). If casr parity is later judged to require memory, it's a `memory: [...]` envelope addition under a bumped `schema_version` — non-breaking, tracked as follow-up. Flagged so the omission is explicit, not silent.
